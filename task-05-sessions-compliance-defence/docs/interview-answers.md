## Part 1: Sessions Architecture & Security

### Question 1: What should a secure browser session look like? Name every property and what each one prevents.
A secure browser session in a modern web application must be constructed as a cryptographically unguessable, high-entropy token stored server-side and transmitted exclusively via an HTTP cookie hardened with strict defense-in-depth flags. 

The token itself should be a 256-bit random sequence generated by a cryptographically secure pseudorandom number generator (`crypto.randomBytes(32)`), yielding $2^{256}$ possible combinations to eliminate brute-force predictability. On the server, only the SHA-256 hash of the token should be stored in the database, preventing session hijacking if the database is breached.

The cookie carrying the session must enforce five mandatory properties:
1. **`HttpOnly`**: Blocks client-side JavaScript (`document.cookie`) from accessing the cookie, neutralizing token theft via Cross-Site Scripting (XSS).
2. **`Secure`**: Restricts cookie transmission exclusively to encrypted TLS/HTTPS connections, preventing cleartext packet sniffing across public Wi-Fi or cellular networks.
3. **`SameSite=Lax` (or `Strict`)**: Restricts cookie transmission on cross-site requests, mitigating Cross-Site Request Forgery (CSRF).
4. **`Path=/`**: Restricts the cookie scope to authorized application paths.
5. **`Max-Age` / `Expires`**: Enforces a definitive temporal lifespan (e.g. 30 days) to prevent zombie sessions from persisting indefinitely.

### Question 2: What is session fixation, and what prevents it?
Session fixation is an attack where an adversary forces a victim to authenticate using a pre-determined, known session identifier chosen by the attacker. In a vulnerable application, the server might issue a session token to an anonymous visitor. The attacker takes this identifier, embeds it into a malicious hyperlink (e.g., `https://app.fieldlog.internal/login?session_id=ATTACKER_ID`), and tricks the victim into clicking it and entering their credentials. If the server validates the login without regenerating the session token, the existing identifier is elevated to an authenticated state. Because the attacker already knows this identifier, they can immediately access the victim's account.

Session fixation is completely prevented by **mandatory session regeneration upon authentication state transition**. Whenever an unauthenticated user logs in, elevates privileges, or switches roles, the server must discard any pre-existing session token and generate a completely fresh, high-entropy cryptographic token. By destroying the pre-authentication token and issuing a new one, any session identifier previously known to the attacker is rendered useless before authenticated data can be accessed.

### Question 3: Are tokens (e.g. stateless JWTs) better than server-side sessions? Answer for your own application, not in general.
For FieldLog specifically, **server-side database-backed sessions are vastly superior to stateless JWTs**.

While stateless JWTs reduce database read overhead in high-throughput consumer platforms, they introduce severe security flaws that are unacceptable in FieldLog’s environmental compliance domain:
1. **Instant Revocation is Impossible with Pure JWTs**: Under FieldLog PRD FR-57 and Task 5 rules, if an organisation admin deactivates an employee due to suspected misconduct, or if a supervisor loses their phone on a site, their access must terminate immediately. With stateless JWTs, a compromised token remains valid until its expiration timestamp unless the server maintains a stateful token blacklist—which defeats the entire purpose of statelessness.
2. **Offline-to-Online Session Synchronization**: FieldLog supervisors work offline for days. When they reconnect, their device status must be validated against the server's tenant authorization rules.
3. **Storage Security**: Storing JWTs in browser `localStorage` exposes them to XSS extraction. Storing a hashed session reference in an `HttpOnly`, `Secure` cookie backed by PostgreSQL guarantees that revocation is constant-time ($O(1)$) and centralized.

### Question 4: How would you implement log out of all devices?
To implement "Log Out of All Devices" (Global Session Revocation), the application relies on server-side session tracking where every session row is associated with a foreign key to the `User` entity.

When a user selects "Log Out of All Devices" (or resets their password):
1. **Server-Side Transaction**: The server executes a single atomic database query:
   ```sql
   DELETE FROM "Session" WHERE "userId" = $authenticatedUserId;
   ```
2. **Audit Logging**: An immutable audit row is written to `AuditEvent`:
   `action: "GLOBAL_LOGOUT", userId: $userId, timestamp: NOW()`.
3. **Client Cookie Invalidation**: The server responds to the calling browser with an expired `Set-Cookie` header (`Max-Age=0`) to clear the local cookie.
4. **Immediate Universal Invalidation**: Because all other devices (the supervisor’s tablet in the site trailer, their personal phone, and office desktop) hold session cookies whose matching records were deleted from PostgreSQL, the very next HTTP request dispatched by any of those devices will fail the session lookup query. The authentication middleware immediately catches the missing session, rejects the request with `HTTP 401 Unauthorized`, and redirects the user to the login screen.

### Question 5: How do you invalidate existing sessions on a password change?
When a user updates their password—either through routine profile settings or via an emergency password reset link—all pre-existing sessions must be terminated to ensure that any compromised device or unauthorized session is immediately severed.

The mechanism is implemented as an atomic database transaction:
```typescript
await prisma.$transaction([
  // 1. Update the user password hash with Argon2id
  prisma.user.update({
    where: { id: userId },
    data: { passwordHash: newHashedPassword }
  }),
  // 2. Delete all existing sessions for this user across all devices
  prisma.session.deleteMany({
    where: { userId: userId }
  }),
  // 3. Increment a tokenVersion or securityStamp counter
  prisma.user.update({
    where: { id: userId },
    data: { tokenVersion: { increment: 1 } }
  })
]);
```
By coupling the credential update and session deletion within a single serializable database transaction, the application guarantees that a password change can never succeed without simultaneously destroying all active session tokens. If the user changed their password on their phone, they are issued a fresh session token, while their tablet and laptop are logged out instantly.

### Question 6: What do the HttpOnly, Secure, and SameSite cookie flags protect against, and what does each fail to protect against?
These three flags form the perimeter of browser cookie security, each addressing distinct attack vectors:

1. **`HttpOnly`**:
   * *Protects Against*: Stored and reflected Cross-Site Scripting (XSS) attacks attempting to read session tokens via `document.cookie`.
   * *Fails to Protect Against*: In-browser request execution. If an attacker injects malicious JavaScript, they cannot steal the token, but they can still use `fetch()` within the victim’s authenticated browser to issue unauthorized requests that automatically include the cookie.
2. **`Secure`**:
   * *Protects Against*: Man-in-the-Middle (MitM) eavesdropping and packet sniffing by ensuring the cookie is transmitted only over encrypted TLS (HTTPS).
   * *Fails to Protect Against*: Attacks on the client machine itself (local malware, spyware, physical terminal access, or browser debugging tools).
3. **`SameSite=Lax` (or `Strict`)**:
   * *Protects Against*: Cross-Site Request Forgery (CSRF). Browsers refuse to attach the cookie on cross-site form `POST`s or state-mutating requests originated from external third-party sites.
   * *Fails to Protect Against*: Same-origin attacks, cross-site scripting on the same domain, or top-level navigational `GET` requests (under `SameSite=Lax`, top-level links still transmit cookies).

### Question 7: What is the difference between a 401 and a 403, and how should the interface treat them differently?
HTTP 401 and HTTP 403 represent two fundamentally distinct failure modes in identity architecture:

* **`HTTP 401 Unauthorized` (Unauthenticated)**:
  * *Meaning*: The user's identity is unknown to the server. The request lacks valid credentials, the session token has expired, or the cookie was cleared.
  * *UI Handling*: The application must immediately redirect the user to the login screen (`/sign-in?mode=sign-in&redirect=/reports`), caching their attempted destination URL so they can be returned there after authenticating.
* **`HTTP 403 Forbidden` (Unauthorized)**:
  * *Meaning*: The user's identity is verified, but their authenticated account lacks permission to access the requested resource. For example, a field supervisor trying to access the Organisation Admin billing portal (`/admin/billing`).
  * *UI Handling*: The application must **not** redirect to the login screen (logging in again will not change their role). Instead, the UI must keep the user logged in, render an explicit, accessible access-denied view ("Access Restricted: This view requires Administrator privileges"), and provide a navigation link back to their authorized dashboard (`/today`).

## Part 2: Session Mechanics & Boundary Control

### Question 8: Why must logout be handled on the server rather than the front end, and what exactly stays alive if it is not?
Handling logout strictly on the frontend (e.g., clearing local React state, deleting browser localStorage, and redirecting to `/sign-in`) is a severe security vulnerability.

If logout does not contact the server:
1. **What Stays Alive**: The session record remains completely active, valid, and unexpired inside the server's PostgreSQL database table.
2. **The Security Defect**: HTTP cookies cannot always be reliably cleared by client-side JavaScript if they were set with `HttpOnly` and `Path=/`. Even if the client attempts to remove the cookie, an adversary who intercepted the session token earlier (or who uses the browser's back button / network history on a shared terminal) can simply copy the token into another browser. Because the server was never told to terminate the session, the backend will treat every request sent with that token as valid.

A secure logout must be executed as a server-side API call that deletes the session record from the database using `DELETE FROM "Session" WHERE "sessionToken" = SHA-256($token)` and instructs the browser to destroy the cookie by returning `Set-Cookie: fieldlog_session=; Max-Age=0; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT`.

---

### Question 9: What is the difference between authentication and authorisation, and which one does a protected route need?
* **Authentication (AuthN)** is the verification of identity: answering the question *"Who are you?"* It proves that the caller possessing a session cookie is indeed user `Aliyu Bakare` based on valid credentials supplied earlier.
* **Authorisation (AuthZ)** is the verification of permission: answering the question *"Are you permitted to perform this specific action on this specific resource?"* It determines whether user `Aliyu Bakare` holds the necessary role (`ADMIN` vs. `SUPERVISOR`) and organisation tenant membership to read or modify a given record.

**A protected route strictly requires BOTH.** 
Authentication is merely the baseline prerequisite: confirming the user is logged in. If a protected route (such as `/admin/users` or `/api/billing`) only checks authentication, an ordinary supervisor can access administrative tools or view another company's records simply by logging in with their own valid supervisor account. The protected route must first authenticate the caller, and then immediately enforce authorization by verifying that `session.user.role === 'ADMIN'` and `resource.organisationId === session.user.organisationId`.

## Part 3: Compliance, Deletion & The Law

### Question 10: A user asks you to delete their account. Walk me through what happens, from the request to the data being gone.
When an employee requests account deletion in FieldLog, the system initiates a structured, compliant three-phase lifecycle:

1. **Phase 1: Immediate Deactivation & Session Severance (Day 0)**:
   * The request is authenticated. The user's status is updated to `DEACTIVATED`.
   * An atomic query deletes all active sessions from the `Session` table, immediately revoking access across all devices.
   * `deletedAt` is stamped with the current timestamp.
   * An immutable audit record (`AuditEvent`) logs the deletion request.
2. **Phase 2: The 14-Day Cooling-Off Grace Period (Days 1–14)**:
   * The account remains locked and inaccessible. No data is purged yet.
   * This window protects against accidental deletion, account takeover sabotage, and allows administrative challenge.
3. **Phase 3: Automated Batch Purge & Anonymisation (Day 15)**:
   * A scheduled background worker identifies expired grace-period records.
   * In a single database transaction:
     - Authentication credentials (`passwordHash`, salt, reset tokens) are hard-deleted.
     - Personal identity fields are permanently anonymised: `name` becomes `"Former Supervisor [UUID]"`, `email` becomes `"anon_[UUID]@fieldlog.internal"`, and phone numbers are purged.
     - Immutable site entries, daily reports, and audit logs are preserved with the anonymized foreign key to fulfill the statutory 7-year environmental compliance retention mandate.

### Question 11: Which data would you refuse to delete on a deletion request, and on what basis?
In FieldLog, we strictly **refuse to delete four categories of data**:
1. **Approved Daily Site Reports and Revision Snapshots (`ReportRevision`)**.
2. **Environmental Site Capture Entries, Work Statuses, and Contamination Quantities (`EntryVersion`)**.
3. **Site Evidence Photographs and GPS Coordinates (`Photo`)**.
4. **Financial Payment Records and Billing Ledgers (`Payment`)**.

**The Legal Basis for Refusal**:
Under **GDPR Article 17(3)(b) & (e)** and **Nigeria Data Protection Act (NDPA 2023) Section 34(2)**, the right to erasure is explicitly overridden when data retention is required:
* For compliance with a statutory legal obligation (such as Nigerian environmental protection laws under NESREA and NUPRC/EGASPIN, which mandate that hazardous waste cleanup records be preserved for regulatory audits).
* For the establishment, exercise, or defence of legal claims (tort liability for environmental contamination).
* For statutory tax accounting under corporate law (Companies and Allied Matters Act / FIRS).

We fulfill the user's data protection rights by completely anonymising their personal identity, but the factual site records remain intact.

### Question 12: What happens to your backups when a user is deleted?
When a user is deleted or anonymised in the production PostgreSQL database, the historical database backups (WAL archives and daily snapshots) still contain the user's personal data at the point in time the snapshot was captured.

It is technically impossible and hazardous to decrypt and alter historical backup archives to remove a single row, as doing so would invalidate backup cryptographic hashes and destroy disaster recovery integrity.

**How Compliance is Maintained**:
1. **Strict 30-Day Backup Expiry**: All automated database backups in cloud object storage are governed by immutable lifecycle policies that permanently delete snapshots after **30 days**. Thus, any historical personal data naturally self-destructs within a month.
2. **Restoration Tombstone Replay**: If a disaster recovery event forces FieldLog to restore an older database snapshot, our recovery runbook automatically re-executes the append-only `AuditEvent` log of anonymisation events. The restoration script scans all `USER_ANONYMISED` audit entries and re-applies the anonymisation updates to the restored database before the application is opened to traffic, ensuring deleted users are never accidentally resurrected.

---

### Question 13: What is the difference between anonymising and deleting, and when is anonymising sufficient?
* **Deleting (Hard Deletion)** is the complete physical removal of a database row and its related child records (`DELETE FROM "User" WHERE id = $id`). The data ceases to exist in any form.
* **Anonymising** is the irreversible transformation of personal identifiers within a record such that the data subject can no longer be identified, directly or indirectly, by anyone using any reasonable means, while preserving the parent row and its non-personal foreign-key relations.

**When Anonymising is Sufficient**:
Under GDPR (Recital 26) and NDPA regulations, **anonymised data is no longer personal data**. 
Anonymisation is legally and technically sufficient—and often required—when:
1. The records are linked to external relational dependencies (such as environmental audit reports or financial transactions) that would suffer referential integrity corruption if foreign keys were orphaned or hard-deleted.
2. The business needs to preserve statistical, operational, or legal records (e.g. proof that 500 metric tonnes of contaminated soil were excavated on October 12th) without maintaining the identity of the specific human being who logged the entry.

### Question 15: A customer says they want to use AI to improve their operations. How do you respond?
My immediate response is: **"Before we talk about AI models, let's look at your data architecture and identify the single most expensive, manual bottleneck in your daily operations."**

Customers frequently treat "AI" as a magic wand, asking for generative chat interfaces or automated agents before their baseline systems are capable of reliable data capture. I explain that an AI model is only as effective as the quality, structure, and integrity of the data fed into it. If an environmental firm currently shares photos over WhatsApp and tracks excavation tallies in paper logbooks, deploying an LLM will merely produce hallucinated summaries based on incomplete fragments.

My framework for responding:
1. **Audit the Data Pipeline**: Establish structured, offline-first digital capture so clean, verified records exist.
2. **Identify Specific High-Value Use Cases**: In FieldLog, we restrict AI to two explicit, opt-in capabilities: drafting suggested report summaries from structured notes (FR-58) and semantic meaning search across historical incidents (FR-59).
3. **Enforce Human-in-the-Loop Verification**: An AI suggestion must never automatically approve a report or sign off on statutory compliance. A human engineer must always inspect, edit, and certify the output.

### Question 16: What is the difference between a RAG system and a fine-tuned model for an enterprise deployment?
* **Retrieval-Augmented Generation (RAG)**: Keeps the foundation LLM frozen. When a user asks a query, the system converts the query into a vector embedding, searches a private enterprise database (e.g. PostgreSQL with `pgvector`) for relevant document chunks using cosine similarity, injects those retrieved chunks into the prompt context window, and instructs the LLM to answer strictly based on that retrieved evidence.
* **Fine-Tuning**: Takes an existing model and updates its internal neural network weights by training it on a specialized dataset of domain-specific input/output pairs.

**Trade-offs in Enterprise Deployment**:
* *Data Freshness*: RAG updates instantly as new reports are written (updating database vectors in real time); fine-tuning requires expensive, periodic model retraining.
* *Auditability & Hallucination*: RAG provides verifiable citations pointing to the exact database chunk used to formulate the answer; fine-tuned models cannot cite sources and can hallucinate with high confidence.
* *Access Control*: RAG allows strict tenant isolation (filtering vector search by `organisationId`), ensuring confidential data never crosses company boundaries; fine-tuning bakes knowledge directly into neural weights, risking cross-tenant data leakage.

For enterprise compliance applications, RAG is almost universally the correct architecture.

### Question 17: How do you evaluate whether an AI agent is working correctly in production?
Evaluating an AI agent in production cannot rely on gut feeling or generic benchmark scores; it requires continuous, automated evaluation across three empirical dimensions:

1. **Retrieval Evaluation (Context Precision & Recall)**: Measure whether the vector retrieval engine actually fetched the correct database chunks required to answer the query. We track the Mean Reciprocal Rank (MRR) and NDCG to ensure the top-ranked retrieved chunks contain the ground-truth site records.
2. **Generation Evaluation (Faithfulness & Hallucination Detection)**: Use automated evaluation harnesses (e.g., Ragas or LLM-as-a-Judge) to score whether every claim in the generated output is strictly grounded in the retrieved context. If an AI summary mentions *"500 barrels recovered"* but the retrieved site note states *"200 barrels"*, the faithfulness score drops to zero, triggering an automated alert.
3. **Human Acceptance & Latency Telemetry**: Track real human operational behavior:
   * How often do supervisors click "Accept" vs. "Edit" vs. "Reject" on AI-generated draft summaries?
   * Monitor end-to-end latency to ensure semantic search responds within our strict performance budget (**NFR-21: sub-2-second p95 latency**).

## Part 5: Front-End State & Architecture

### Question 18: How do you decide between local component state, context, and an external state manager?
I decide based on the **scope of data ownership, update frequency, and lifecycle persistence**:

1. **Local Component State (`useState` / `useReducer`)**:
   * *When to Use*: Data that belongs strictly to a single UI component or its immediate children and does not need to outlive the component's unmounting.
   * *Examples*: Form input values, password visibility toggles (`showPassword`), dropdown open/closed states, inline validation errors.
2. **React Context (`useContext`)**:
   * *When to Use*: Global or branch-level configuration state that changes infrequently but is read by many deeply nested components.
   * *Examples*: Active UI color theme, localization/language preferences, current user role metadata. Context is unsuited for high-frequency updates because any state change re-renders all consumer components.
3. **External State Manager (Zustand, Redux)**:
   * *When to Use*: High-frequency, complex client state that requires fine-grained selector-based re-renders, complex asynchronous state machines, or cross-tab synchronization that would otherwise trigger massive render waterfalls.
   * *Threshold in FieldLog*: We actively avoided external libraries because our primary state lives either in the URL query string (for filter modes) or in **IndexedDB** (for durable offline field capture).

---

### Question 19: How do you handle server state, as distinct from client state?
**Client state** is ephemeral UI memory owned by the browser (active tab, modal open status, uncommitted form inputs). **Server state** is data owned, persisted, and controlled by the remote server and database (project site lists, submitted daily reports, user accounts).

Handling server state correctly requires recognizing that **the client does not own server data; it only holds a temporarily cached snapshot that is potentially stale**.

In FieldLog:
1. **Server Components for Initial Rendering**: We fetch server state directly on the server in React Server Components, eliminating client-side loading spinners and waterfall network requests.
2. **Mutations via Server Actions**: Data modifications execute as atomic Server Actions or REST endpoints that mutate the database, revalidate Next.js cache paths (`revalidatePath`), and return fresh server state.
3. **Optimistic Updates for Offline Capture**: For offline field capture, we write entries immediately to local IndexedDB, providing instant UI response, while maintaining an outbox queue that reconciles with server state upon network reconnection using client UUIDs for strict idempotency.

### Question 22: Wrong-Answer Analysis
**The candidate's statement:**
> *"For GDPR compliance we added a delete account button that removes the user's row from the database immediately, so we are fully compliant with the right to be forgotten. We also keep backups for a year in case anyone needs their data restored."*

This candidate demonstrates dangerous, surface-level compliance understanding that exposes their organisation to severe legal and technical liability.

#### The Flaws Analyzed in Order of Severity:
1. **Critical Legal Exposure: Immediate Deletion Violates Statutory Retention & Audit Laws**:
   The candidate naively believes the "right to be forgotten" is an absolute, unconditional mandate. In any commercial business with transactions or statutory reports, deleting a user row immediately destroys financial accounting ledgers (violating corporate tax law) and wipes authorial evidence on engineering/safety logs. Under GDPR Article 17(3), legal obligations take precedence over erasure requests. The correct design is **anonymisation of personal identity** while retaining immutable records.
2. **Critical Legal & Technical Conflict: Retaining Backups for a Year Violates Erasure**:
   The candidate claims to be "fully compliant", yet keeps database backups containing the deleted user's plaintext personal data for a full year. If those backups are ever restored during disaster recovery, the deleted user is resurrected! Retaining unrestored personal data in backups beyond reasonable operational retention windows without tombstone replay mechanisms violates GDPR storage limitation principles.
3. **Severe Technical Flaw: Immediate Hard Deletion Corrupts Database Referential Integrity**:
   Executing an immediate `DELETE FROM "User"` will either crash the database with Foreign Key constraint violations (if child tables reference `userId`) or cascade-delete all of the user's historical reports, destroying company records.
4. **The Correct Design**:
   Implement a **14-day grace period** (soft delete), immediately revoke all sessions, purge authentication credentials, anonymise personal data fields (`name`, `email`, `phone`), retain statutory business and environmental records with anonymized foreign keys, and enforce a rolling **30-day backup destruction policy** with tombstone replay runbooks.
