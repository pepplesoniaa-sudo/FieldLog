# Email Verification Architecture: CSPRNG, Expiry & Threat Modeling

## 1. Cryptographic Code Generation (`crypto.randomInt`)
FieldLog generates email verification codes using Node.js's built-in Cryptographically Secure Pseudorandom Number Generator (CSPRNG):

```typescript
const verificationCode = crypto.randomInt(100000, 1000000).toString();
```

### Why `Math.random()` is Strictly Banned:
Standard `Math.random()` functions are implemented using predictable Linear Congruential Generators (LCG) or xorshift algorithms. They are designed for mathematical simulations and graphics, not security. If an attacker captures 2 or 3 consecutive verification codes generated by `Math.random()`, they can reconstruct the internal PRNG state seed using tools like Z3 theorem provers and predict the exact 6-digit codes generated for subsequent target user registrations with 100% accuracy. `crypto.randomInt` draws entropy directly from the operating system kernel (`/dev/urandom` or Windows CryptGenRandom), guaranteeing cryptographic unpredictability.

---

## 2. Attack Vector Against Predictable Codes
If an application uses predictable pseudo-random codes, an attacker can bypass email verification entirely within the 10-minute expiry window. The attacker creates an account to observe the current PRNG output sequence, mathematically calculates the next sequence values, and immediately initiates a registration for a targeted enterprise email address (e.g. `director@remediation.co.uk`). 

Because the attacker already knows the exact 6-digit code that was dispatched to the director's inbox, they submit the verification code immediately without ever accessing the director's email account. Even with a rate limit of 5 requests per hour, an attacker armed with a predictable sequence requires exactly **one single attempt** to verify the account, hijacking enterprise ownership before the legitimate owner opens their inbox.

---

## 3. Expiry Window Justification: Why 10 Minutes is the Optimal Balance
We selected an expiration window of exactly **10 minutes** (PRD FR-62). This choice was balanced against two competing operational constraints:

1. **How Long Real Users Actually Need**:
   In construction and environmental remediation, supervisors frequently register while walking site perimeters on mobile devices. A short 2-minute window is hostile: email delivery across corporate Exchange filters can take 45–90 seconds; switching apps to a corporate mail client, completing corporate biometric re-authentication, and returning to the browser takes an average of 3 to 6 minutes. A 10-minute window comfortably accommodates realistic human latency without triggering frustrating expirations.
2. **What the Window Costs in Attack Surface**:
   A 6-digit code has exactly $1,000,000$ possible combinations. Coupled with our rate limit enforcing a hard lockout after **3 failed verification attempts** (`attempts >= 3` in `EmailToken`), an attacker has at best a $3 / 1,000,000 = 0.0003\%$ chance of guessing the code before the token is permanently invalidated. Expanding the window from 2 to 10 minutes does not increase the brute-force success probability because the attempt limit halts attacks after 3 guesses regardless of elapsed time.
